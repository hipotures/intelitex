# Pomiary odczytu i zapisu JSON — 2026-09-27

Pomiar rzeczywistych danych `salvation-02`, bez benchmarków SQLite i bez zmian
w serializerach aplikacji. JSON pozostaje źródłem prawdy; przyszłe SQLite ma być
odtwarzalnym cache’em. Wszystkie zapisy wykonano w usuwanych katalogach
tymczasowych pod `/home/user/translations`, na tym samym filesystemie co oryginały.

## Metoda i ograniczenia

- Python 3.14.4, orjson 3.12.0, Linux, 2 vCPU, około 3,9 GB RAM, bez swapu.
- `/home/user` to ext4 na `/dev/sdb`, dysk QEMU oznaczony jako nierotacyjny.
  Nie oznacza to potwierdzenia rodzaju ani obciążenia fizycznego storage hosta.
- 30 prób na operację, po rozgrzewce, losowa kolejność wariantów w każdej rundzie.
  Test dziesięciu zmian: 10 prób, więc jego p95 jest maksimum z tych prób.
- Ciepły cache systemu plików; bez `drop_caches`. To nie jest pomiar zimnego dysku.
- Działający serwer pozostał uruchomiony. Nie izolowano CPU ani hosta VM.
  Duża zmienność występuje również w czasie CPU procesu; same dane nie pozwalają
  ustalić jej przyczyny. Nie należy traktować median jako stałej wydajności serwera.
- Czasy oznaczają pojedyncze operacje, nie żądania HTTP ani ładowanie strony.
  Nie potwierdzają samodzielnie źródła zgłoszonego opóźnienia 16 sekund.
- Pomiary serializacji obejmują przygotowanie bajtów UTF-8. Testy zapisów
  atomowych zachowują `fsync` pliku, `replace` i `fsync` katalogu.
- `orjson` zainstalowano do `/tmp/intelitex-json-bench-deps`; nie zmieniono
  `pyproject.toml`, lockfile ani zależności aplikacji. Sprawdzono równość wartości
  po round-trip dla pięciu badanych dokumentów, nie ogólną zgodność serializerów.

Aktualne osiem tabel stanu zajmuje łącznie około 4,28 MB. Jedna zmiana statusu:

- osiem odczytów JSON, łącznie 4 198 538 B;
- trzy zapisy, łącznie 78 128 B (tabela segmentów, commit i HEAD);
- osiem wywołań `fsync`;
- ponowne liczenie checksum wszystkich tabel, a dla niezmienionych tabel także
  odczyt i ponowna weryfikacja istniejącego obiektu.

To **nadmiarowe przetwarzanie i odczyty**, nie przepisywanie całych 4,28 MB.
Kod już współdzieli niezmienione obiekty na dysku. Mediana CPU publikacji to
60,63 ms z 66,39 ms czasu rzeczywistego.

Test zadania obejmuje prawdziwe zachowanie nowego rejestru: kopię ograniczonej
historii, checksum, zapis wersji rekordu i podmianę indeksu. Nie jest to sam zapis
109 KB. Rejestr startuje z kopii 53 rekordów; archiwum migracji nie jest czytane.

## Batching i JSONL

Dziesięć zmian jednego pola dużego manifestu, dokument już w RAM:

| Sposób | p50 ms | p95 ms |
|---|---:|---:|
| Dziesięć pełnych atomowych zapisów | 3180,02 | 4485,08 |
| Dziesięć zmian i jeden atomowy zapis | 379,60 | 519,04 |

To kontrolowany eksperyment pokazujący koszt powtarzania zapisów, **nie dowód**,
że konkretne kliknięcie obecnie zapisuje `book.json` dziesięć razy.

Dopisanie syntetycznego rekordu JSONL (855 B, wraz z serializacją) do istniejącego
pliku: p50 0,025 ms bez `fsync`, 0,906 ms z `fsync` pliku. Wariant bez `fsync`
nie ma takiej samej trwałości. Dopisanie zdarzenia nie zastępuje losowej edycji
pola ani atomowej transakcji między kilkoma plikami. JSONL wymagałby osobnej
obsługi odtwarzania, uciętego ostatniego wpisu, blokad i kompaktowania.

## Wnioski do implementacji

1. Zachować atomowe zapisy i synchronizację. Ten pomiar nie uzasadnia wyłączania
   `fsync`: główny koszt dużych dokumentów leży w przetwarzaniu JSON i kopiowaniu.
2. Ograniczać ponowne odczyty, fingerprinty i `deepcopy` w obrębie jednej operacji.
   Istniejący cache manifestu już pomaga odbiorcom tylko do odczytu.
3. W stanie śledzić zmienione tabele zamiast ponownie przetwarzać wszystkie.
   Trzeba zachować wykrywanie konfliktów i spójność commit/HEAD/checksum.
4. Rozważyć `orjson` dla odczytu i zapisu artefaktów, po testach kontraktów typów
   i wartości. **Nie podmieniać automatycznie `digest`**: reprezentacja kanoniczna
   ustala istniejące identyfikatory, fingerprinty i checksum.
5. Łączyć zmiany należące do jednej transakcji. Debounce między żądaniami wymaga
   świadomego kontraktu potwierdzania trwałego zapisu; samo odłożenie zapisu do
   shutdown nie jest równoważnym rozwiązaniem.
6. JSONL rozważać dla dzienników; pomiar nie uzasadnia zmiany całego stanu na log.
7. Aby wyjaśnić 16-sekundową stronę, osobno policzyć powtórzenia i profilować
   pełne żądanie. Ten benchmark nie mierzy sieci, renderowania ani całego API.

Nie zmieniono kodu produkcyjnego ani danych użytkownika. SHA-256 wybranych
dokumentów źródłowych i aktualnego checkpointu pozostały identyczne; osobno
potwierdzono niezmienność indeksu i wszystkich 53 referencjonowanych rekordów
zadań. Nie wykonywano publish książki, tłumaczeń ani restartu serwera.
Końcowy skrypt przeszedł także pełne uruchomienie kontrolne (po dwie próby),
z `sqlite3.connect` zastąpionym funkcją rzucającą wyjątek. Żadna ścieżka benchmarku
nie próbowała otworzyć połączenia SQLite.

## Powtórzenie

Z katalogu repozytorium, z oddzielną opcjonalną zależnością benchmarku:

```bash
uv pip install --target /tmp/intelitex-json-bench-deps orjson==3.12.0
PYTHONPATH=/tmp/intelitex-json-bench-deps:. .venv/bin/python tools/benchmark_json.py \
  --workspace /home/user/translations/salvation-02 \
  --output /tmp/intelitex-json-benchmark.json --samples 30
```

Ścieżki to argumenty konkretnego uruchomienia, nie konfiguracja aplikacji.
Bez orjson skrypt pomija tylko jego warianty. Uruchamiać bez równoległego
tłumaczenia/mutowania badanych danych; kontrola hashy wykrywa zmianę w trakcie.
Oryginały są tylko czytane, zapisy dotyczą automatycznie usuwanych kopii.
